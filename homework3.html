Homework 3 - Toy ECC scheme vs Caesar cipher, and two attacks

A hybrid EC-ElGamal toy scheme on secp256k1 with a restricted private key (Homework 1.1 curve, real 256-bit parameters), the Caesar cipher, and a statistical and an algebraic attack. The live demos run in your browser with no libraries; the tables report the full experiments of Homework3.java (Java 21, standard library only, fixed seed; it reads corpus.txt and test.txt from the same folder and runs with java Homework3.java).

1. Toy ECC scheme: encrypt and decrypt

Homework 1.1 only maps a private key k to a public key Q = k·G. To encrypt a message I add the standard ECIES-style layer:

StepOperationRole of the keys
Key generationk random in [1, 220] (restricted), Q = k·Gk is the private key and stays secret; Q is the public key.
Encryptionfresh random 256-bit r; C1 = r·G; S = r·Q; keystream = SHA-256(S.x ‖ counter); C2 = m ⊕ keystreamr is a one-time ephemeral key. Only the public key Q is needed.
DecryptionS = k·C1 (equals k·r·G = r·Q), same keystream, m = C2 ⊕ keystreamOnly the holder of k can rebuild the shared secret S.

2. Caesar cipher: encrypt and decrypt

Each letter is shifted by k positions in the alphabet (mod 26); case and punctuation are kept. Decryption shifts by -k. The same key is used on both sides (symmetric), and there are only 25 non-trivial keys.

Common pointBoth are "encrypt by combining the message with key-dependent material, decrypt by undoing it". Both are completely broken if the key space is small enough to enumerate.

Caesar only relabels the letters, so every letter-frequency statistic is preserved (sorted letter counts are identical to the plaintext). The ECC ciphertext is a message XORed with a hash of an elliptic-curve point and looks uniform: nothing about the language leaks.

4. Statistical cryptanalysis of the Caesar cipher

Algorithm. Build a language model from a corpus (about 300,000 letters of English prose from the Python documentation). For each of the 26 candidate keys, decrypt the ciphertext and score how English the result looks; return the best key. Four scorers were compared:

  • peak = e: the most frequent cipher letter is assumed to be e (letter-frequency analysis).
  • chi-square between the decrypted letter counts and the corpus frequencies.
  • unigram / bigram / trigram log-likelihood (n-gram scoring, add-0.5 smoothing).

Exhaustive search of the 25 keys is built into every scorer: the statistics decide which candidate is the real plaintext automatically.

Effectiveness and limitations

  • From about 20-40 letters the key is recovered almost always; n-gram scorers are clearly better on short texts. A second, narrative-prose test text gave the same picture (bigram LL 94% at 10 letters, 100% from 20).
  • The shortcut "most frequent letter is e" is fragile: it needs hundreds of letters and still fails about 29% of the time on legal text at 320 letters.
  • Very short texts are genuinely ambiguous: with bigrams the true key ranks first in 35% of trials at 3 letters, 79% at 5 and 92% at 8.
  • No scorer wins every time. On the 27-letter message above, bigram LL chose key 22 while chi-square, unigram and trigram found the right key 7.
  • The attack needs a model of the right language and domain. On uniformly random "plaintext" chi-square succeeds in 5.0% of trials, close to chance (1/26 = 3.8%).

5. Attack on the restricted ECC private key

The attacker sees only Q, G and the ciphertext, and wants k with k·G = Q.

  • Brute force: compute G, 2G, 3G, ... until the point equals Q. Up to K additions.
  • Baby-step giant-step: write k = i·m + j with m = ⌈√K⌉. Store the baby steps j·G in a table, then walk Q - i·m·G until a value is in the table. About √K time and memory.

Why it would not work against a properly configured ECC scheme

  • With a full private key, n ≈ 2256. Brute force is hopeless and the best generic attacks (BSGS, Pollard's rho) need about √n = 2128 group operations. BSGS would also need about 2128 stored points, so in practice rho (negligible memory) is the generic attack to consider.
  • There is no statistical foothold: the keystream is a hash of a curve point, and the measured ciphertext is uniform (section 3).
  • Caution: a 128-bit private-key range is not safe either, because √K = 264 operations is within reach of large-scale hardware. Security is roughly half the key length in bits.

6. Which weaknesses come from where (optional)

From the restricted key space

  • Q reveals k in about √K steps, so every past and future message encrypted to Q is broken (no forward secrecy).
  • If the ephemeral r were also small, C1 alone would give r, hence S = r·Q, without ever touching k. Here r is full size.

From the design of the toy scheme (independent of key size)

  • Malleability: there is no authentication. An attacker who knows part of the plaintext can edit the ciphertext without the key. In the program, XORing at a known position turned MIDNIGHT into NOON TIM and the forged ciphertext decrypted without any error. Fix: a MAC over C1 and C2.
  • A wrong key gives silent garbage instead of an error, for the same reason.
  • r must be fresh and unpredictable every time; reusing it reuses the keystream, and the XOR of two ciphertexts equals the XOR of the two plaintexts.
  • The ciphertext length equals the message length, so length leaks.

Caveats: timings come from non-optimised Java (BigInteger, affine coordinates) in one container; the corpus (Python documentation) differs in domain from the test texts, so short-text success rates are probably a little pessimistic; this is a teaching sketch, not a vetted construction.
