Only the very first step is random. Everything after it is a deterministic function of the entropy, which is exactly why a few words are enough to back up an unlimited number of accounts on many chains.

3. Role of each standard and primitive

PieceYearWhat it does in the walletType
BIP-392013 Turns random entropy (128-256 bits) into a list of words from a 2048-word list (11 bits per word). A few extra bits, taken from SHA-256 of the entropy, are appended as a checksum (4 bits for 12 words, 8 bits for 24). The mnemonic is then stretched into a 512-bit seed with PBKDF2-HMAC-SHA512, 2048 iterations, salt = "mnemonic" + passphrase. encodingchecksumderivation
BIP-322012 Builds a whole tree of keys from one seed. Master key and chain code = HMAC-SHA512(key="Bitcoin seed", seed) (left 32 bytes = key, right 32 bytes = chain code). Each child is HMAC-SHA512(chain code, data || index), where data is the parent private key (hardened, index ≥ 231) or the parent compressed public key (non-hardened). The child key is the HMAC left half added to the parent key mod n. derivation
BIP-442014 A convention, not an algorithm: it fixes the meaning of each level of the tree, m / purpose' / coin_type' / account' / change / address_index. Ethereum has coin type 60 (registered in SLIP-44), so the first account of most wallets is m/44'/60'/0'/0/0. derivation (path convention)
secp256k12000 (SEC 2) Elliptic curve y² = x³ + 7 over the prime field with p = 2256 − 232 − 977, base point G of prime order n ≈ 2256. Public key Q = k·G is easy to compute and hard to invert (ECDLP). The same key pair is used by ECDSA to sign transactions. It is the same construction as in Homework 1.1, with a 256-bit prime instead of 17. public-key crypto
Keccak-2562008 design, used by Ethereum since 2015 Hash function with 256-bit output. The address is the last 20 bytes of Keccak-256 of the 64-byte public key (x || y, without the 0x04 prefix). It shortens the key to 160 bits and hides the public key until the first signature. hashing
EIP-552016 Adds a checksum to the address without changing its length: hash the 40 lowercase hex characters (as ASCII text) with Keccak-256; each letter a-f is written in upper case if the corresponding hex digit of that hash is ≥ 8, otherwise in lower case. A mistyped address fails the check with high probability. checksum carried by an encoding (letter case)

4. Five notions that must not be confused

NotionDefinitionWhere it appears
Key generationProducing a secret from a source of true randomness. It is the only step that cannot be recomputed and the only one that determines the security level (128 or 256 bits of entropy).Choosing the entropy that becomes the mnemonic.
Key derivationDeterministic computation of new keys from an existing secret (and possibly a public path/passphrase). It adds no entropy: the same input always gives the same output, and the security of every derived key is at most the security of the root secret.PBKDF2 (mnemonic → seed), BIP-32 HMAC-SHA512 (seed → master → children), BIP-44 path.
Public-key cryptographyKey pairs (k, Q) with an algebraic relation that is easy in one direction and (believed) infeasible in the other, which allows signing and verifying without sharing a secret.secp256k1: Q = k·G and ECDSA signatures.
HashingA deterministic, keyless, public function from arbitrary input to fixed-size output, designed to be one-way, collision resistant and to behave like a random function (avalanche).Keccak-256 (address, EIP-55), SHA-256 (BIP-39 checksum), SHA-512 inside HMAC/PBKDF2.
ChecksumA few redundant bits computed from the data to detect accidental errors. It protects against typos, not against an attacker (anyone can recompute it).Last bits of a BIP-39 mnemonic (SHA-256), mixed-case letters of EIP-55 (Keccak-256).
EncodingA reversible change of representation with no secret and no security by itself.Entropy ↔ words (11-bit groups), bytes ↔ hex, 0x prefix, compressed public key (02/03 + x), upper/lower case.

Useful test: if you can undo the step with no secret and no search, it is an encoding; if it adds bits that are a function of the data, it is a checksum; if it is one-way and keyless, it is a hash; if it is one-way but takes a secret/salt to produce related secrets, it is derivation; if it produces a key pair with a verifiable algebraic link, it is public-key cryptography.

5. Historical context

1977RSA - first widely used public-key system. Security rests on integer factoring; keys of 2048-3072 bits are needed today. (Elliptic curves for cryptography were proposed independently by Koblitz and Miller in 1985.)
2000secp256k1 is defined in the SECG standard SEC 2. It was almost unused until Bitcoin adopted it in 2009, and Ethereum inherited it.
2001SHA-2 / SHA-512 - NIST standard (FIPS 180-2). Used in the pipeline inside PBKDF2 and HMAC (SHA-512) and for the BIP-39 checksum (SHA-256).
2012BIP-32 - hierarchical deterministic wallets: one seed, a tree of keys. In the same year NIST selected Keccak as the winner of the SHA-3 competition.
2013BIP-39 - mnemonic words and seed derivation, to make seed backups human-friendly.
2014BIP-44 - multi-account, multi-coin path convention.
2015SHA-3 - standardized by NIST as FIPS 202, based on Keccak. The same year Ethereum launched, using the original Keccak-256 submitted to the competition (before NIST modified the padding), which is why Ethereum's "Keccak-256" is not the standard SHA3-256.
2016EIP-55 - mixed-case checksum for addresses, a backwards compatible fix for typos in plain hex addresses.

Reading the timeline: the wallet pipeline is a stack of layers built over almost forty years, each solving a different problem. The older bricks (public-key crypto, SHA-2) are reused unchanged; the newer ones (BIP-32/39/44, EIP-55) are usability and safety layers on top.

6. SHA-2 / SHA-512 versus Keccak / SHA-3

  • Same family, different design. Both are cryptographic hash functions. SHA-2 (SHA-256, SHA-512) uses the Merkle-Damgard construction: a compression function applied block after block, with the final internal state as the digest. Because the digest is the whole internal state, plain SHA-256/512 is vulnerable to length-extension attacks (this is why HMAC is used for keyed hashing).
  • Keccak is a sponge: a 1600-bit state is permuted with Keccak-f[1600]; input is "absorbed" into the first rate bits (1088 for 256-bit output) and the digest is "squeezed" out. The remaining capacity (512 bits) is never output, which prevents length extension. Its internal structure is completely different from SHA-2, which is the point: NIST wanted a backup in case SHA-2 were ever broken. It was not chosen because SHA-2 is weak.
  • Keccak-256 is not SHA3-256. They use the same permutation, rate and capacity, and differ only in the domain-separation/padding byte. Original Keccak pads the message with 0x01 ... 0x80; FIPS 202 first appends the bits 01 and so uses 0x06 ... 0x80. Ethereum was launched with the original, so its hash differs from the standard one for every input.

7. Why several techniques instead of one algorithm?

Each step solves a different problem and needs a different mathematical property. No single primitive has all of them:

LayerProblem to solveProperty neededWhy the others cannot do it
BIP-39 / BIP-32 / BIP-44
key management and derivation		Back up an unlimited number of keys with a short, human-writable secret; organise them per coin and account; derive public keys without the private ones (xpub).Deterministic, one-way, keyed expansion of a secret (HMAC/PBKDF2); a shared path convention so that different wallets find the same accounts.A hash or a curve alone gives one output, not a tree of independent-looking keys; words and paths are about usability and interoperability, not hardness.
secp256k1
public/private key relation, signatures		Prove ownership of an address by signing a transaction that anybody can verify without learning the secret.Trapdoor-like algebraic structure: Q = kG verifiable with signatures, hard to invert (ECDLP).A hash function has no verifiable algebraic relation between input and output, so it cannot give "public verification without the secret" in a compact form.
Keccak-256
hashing		Compress the 512-bit public key to a short, fixed-size identifier; do not expose the public key until needed; also used for transaction and block hashes.One-wayness, collision resistance, uniform-looking output (avalanche).A curve operation is structured (homomorphic), so it is not a good random-looking compressor.
EIP-55
checksum / error detection		Detect typos in a 40-character hex string that is typed or copied by humans, without breaking old software.Cheap, redundant, hard-to-fake-by-accident bits; no secret needed.The checksum must be recomputable by everyone, so it provides no authentication; it only needs to be a deterministic function of the address. Reusing Keccak costs nothing.

Two further consequences of the layering: (i) the chain of one-way steps (seed → key → public key → address) means that revealing an address does not reveal the public key or the private key; and (ii) compartmentalisation: a leaked non-hardened child key plus the parent public key/chain code can reveal the parent, which is the reason hardened derivation (index ≥ 231) is used at the upper levels of BIP-44 paths.

Reading the results

  • Uniformity of the address. Hex digits, bits and bytes of the addresses should be flat. This is a property of Keccak-256 (it behaves like a random function), not of the curve: public keys are structured points, the hash removes that structure. The chi-square on the 256 byte values should be close to its 255 degrees of freedom (|z| < about 3 for a good result).
  • Avalanche at every stage. One flipped bit in a hash input changes about half of the output bits (mean 128 of 256, standard deviation 8). The same holds from private key to address and, more importantly, from the entropy to the final address: the BIP-39 words, PBKDF2, the HMAC-SHA512 chain, the curve and Keccak each add mixing, so two wallets whose entropy differs by one bit have unrelated addresses. This is the hash-like behaviour that the toy elliptic-curve map of Homework 1.1 did not have on its own (there, k→kG kept algebraic structure). Here it is provided by the hash and the HMACs around the curve.
  • Sequential accounts are not correlated. Addresses for index 0, 1, 2, ... of the same seed come out of HMAC-SHA512 with different 32-bit indices, so consecutive Hamming distance is about 80 and the correlation between index and any address byte is about 0.
  • EIP-55 case pattern. Roughly half of the letters are upper case, and the number of letters per address follows a binomial law with mean 15. That also gives the strength of the checksum: a random wrong address has to match about 15 case bits, so it is accepted with probability close to 2-15, about 0.003%. The detection experiment below shows this on random single-character substitutions. Addresses with few letters (for example, all digits) have a weaker checksum.
  • Address space and security. The private key has 256 bits but the address only 160, so each address has on average 296 keys that map to it. Finding a collision costs about 280 hash evaluations (birthday bound), still infeasible. The practical security of the wallet is that of the mnemonic's entropy: 128 bits for 12 words, 256 for 24, plus whatever the passphrase adds. PBKDF2 with 2048 iterations multiplies a guessing attacker's cost by only about 211, so it protects low-entropy phrases poorly: it is not a replacement for entropy.
  • Limits of statistics. Passing uniformity or avalanche tests shows that the outputs look random; it does not prove one-wayness or collision resistance. Those rest on the hardness of the underlying problems (ECDLP for secp256k1, the design analysis of Keccak and SHA-2), not on any test that can be run on a sample.

9. Wallet experiment (MetaMask, Rabby, Rainbow, Exodus, ...)

Procedure to connect each piece of technology to what a real wallet shows. Use a throw-away wallet with no funds and never share a real recovery phrase.

  1. Import the test mnemonic. In a wallet, choose "import wallet" and enter test test test test test test test test test test test junk. The first account must be 0xf39Fd6e51aad88F6F4ce6aB8827279cffFb92266, exactly the address of section 2 (BIP-39 + BIP-32/44 + secp256k1 + Keccak-256 + EIP-55 all agree).
  2. Add accounts. The 2nd, 3rd... accounts correspond to m/44'/60'/0'/0/1, /2, ...: change the last index in the path field above and compare (BIP-44 address_index).
  3. Same words, another wallet. Import the same mnemonic into a second wallet: same addresses (determinism and interoperability of the standards). If a wallet shows a different address, check its derivation path: some hardware-wallet software varies the account level (m/44'/60'/N'/0/0) instead of the address index; try both paths in section 2.
  4. Passphrase. Add a passphrase in section 2 and watch the whole address change (the PBKDF2 salt changes); wallets that support a "25th word" give the same unrelated address.
  5. Checksum. Paste the address in lower case, then in the checksummed form, into the send field or a block explorer. Then change the case of one letter: most wallets and explorers warn that the checksum is invalid (EIP-55), while a fully lower-case address is accepted because it carries no checksum.
  6. Mnemonic checksum. Swap two words, or change the last word, of a valid phrase: wallets reject it with high probability (about 15/16 for 12 words) because the BIP-39 checksum does not match. Check it in section 2.
